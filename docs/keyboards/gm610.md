# Newmen GM610

60 % (61 touches), RGB par touche, tri-mode (USB / Bluetooth ×3 / 2,4 GHz).

## Specs

- MCU : **SinoWealth SH68F90** — la puce se nomme elle-même, `PART = 68 f9 00 00 00`
  relu dans son bloc d'information (`FLASHCON.FAC`, cf. `src/platform/sh68f90/diag.c`)
- Rétroéclairage : RGB par touche, 5 rangées × 14 colonnes
- Sans-fil : **BK3632**, bus bit-bang — les six broches de `src/platform/bb_spi.c`
  correspondent une à une
- USB : `12C9:6001`, `SINO WEALTH` / `Newmen Bluetooth Keyboard`
- Bootloader ISP d'usine conservé, `0xF000`–`0xFFFF`, jamais écrit

## Code options

Identiques, **octet pour octet**, à celles de `eyooso-z11` (BYK901) et `nuphy-air60`
(BYK916) — rien à reprogrammer :

```
Code Option String: A4E063C00F000088
```

Trois conséquences qui comptent ici :

| Option | Valeur | Effet |
| --- | --- | --- |
| `OP_IOV1` | 0 | **P7.1–P7.4 en 5 V** — trois d'entre elles sont des lignes de matrice |
| `OP_SINK0` | 3 | P4.7 (horloge radio) et P7[7:5] en drain fort |
| `OP_ISP` = 1, `OP_ISPPIN` = 1 | — | **aucune entrée ISP matérielle** — voir « Récupération » |

## Brochage

Lignes et colonnes sont **identiques à la `nuphy-air60`** (même design de référence) ;
le GM610 a 14 colonnes utiles au lieu de 16, sur une grille de 21.

| | Broches |
| --- | --- |
| Lignes 0–4 | P7.1 P7.2 P7.3 P5.3 P5.4 |
| Colonnes 0–13 | P5.0 P5.1 P5.2 · P3.5→P3.0 · P2.5→P2.1 |
| Radio | CS P7.4 · SCK P4.7 · MISO P0.6 · MOSI P0.7 · MOT P0.5 · ACK P4.2 |

⚠️ **P5 porte trois choses** : colonnes 0–2 (bits 0–2), lignes 3–4 (bits 3–4, entrée),
puits bleu de la rangée 2 (bit 7). Le firmware d'usine pose la même valeur, `P5CR = 0x87`.

### RGB

Les **14 colonnes sont des sorties PWM** — les mêmes broches que les colonnes de matrice,
que le firmware rebascule en GPIO le temps du scan — et les puits sont **5 rangées ×
3 couleurs**.

| Colonne | 0 | 1 | 2 | 3–8 | 9–13 |
| --- | --- | --- | --- | --- | --- |
| Canal | `PWM40` | `PWM41` | `PWM42` | `PWM05`→`PWM00` | `PWM15`→`PWM11` |

Puits, **vérifiés sur l'appareil** (balayage à un seul canal allumé à la fois) :

| | R | V | B |
| --- | --- | --- | --- |
| L0 | P0.4 | P6.1 | P0.3 |
| L1 | P6.7 | P6.2 | P6.6 |
| L2 | P0.2 | P6.3 | P5.7 |
| L3 | P4.5 | P6.4 | P4.6 |
| L4 | P4.4 | P6.5 | P4.3 |

## Raccourcis

Aux positions **et temporisations** du firmware d'usine.

| | |
| --- | --- |
| `Fn` | rangée basse, colonne 13 |
| `Fn + \` | effet suivant |
| `Fn + [` / `]` | vitesse − / + |
| `Fn + ;` / `'` | luminosité − / + |
| `Fn + D` | balayage de diagnostic des puits RGB |
| **`Fn + B`, ~3 s** | **retour dans le bootloader d'usine** |
| `Fn + Tab`, ~3 s | bascule USB ↔ sans-fil *(radio désactivée, voir plus bas)* |
| `Fn + Q` / `W` / `E` | canaux Bluetooth 1 / 2 / 3 |
| `Fn + G`, ~3 s | liaison 2,4 GHz |

Un maintien « long » vaut **6 000 tours de boucle principale = 3 s**, mesuré sur
l'appareil — cette boucle tourne donc à environ 2 kHz.

## Effets

Deux, volontairement :

- **battement** — deux systoles rapprochées puis une longue diastole, la teinte dérivant.
  C'est un battement de cœur, pas une respiration. Diviseur de vitesse propre, quatre fois
  plus court : au pas commun un cycle durerait dix secondes.
- **goutte d'eau sur le lac** *(défaut)* — chaque frappe jette une goutte, une couronne
  s'en éloigne d'un cran par trame, sa teinte glissant avec la distance. Distance en
  approximation octogonale (`max + min/2`) et non en losange : sur un clavier une rangée
  et une colonne font le même pas physique, les couronnes doivent être rondes.

La position d'une frappe ne passe pas par `kb_process_record()`, qui ne reçoit qu'un code
de touche : `user_matrix.c` tient un instantané par colonne (`user_matrix_pressed()`) que
le moteur d'éclairage interroge, une colonne par sous-trame.

## ⛔ Récupération — à lire avant de flasher

**Cette carte n'a aucune entrée ISP matérielle.** `OP_ISP = 1`, et les 4 096 octets du
bootloader d'usine ne lisent pas un seul GPIO. Il n'existe donc **aucun sauvetage par
combinaison de pads**.

D'où la règle, apprise à la dure le 2026-09-13 : **le firmware doit offrir au moins une
porte vers le bootloader qui ne dépende pas de l'USB.** C'est `Fn + B` maintenu ~3 s, qui
éteint le RGB puis appelle `isp_jump()`.

### ✅ Vérifié le 2026-09-13 : `Fn + B` fonctionne, et le bootloader énumère

Maintenu ~3 s, `Fn + B` fait apparaître `0603:1020` avec ses trois collections — clavier,
canal commande (report 5), canal transfert (report 6) — et **Windows le donne pour
`Status : OK`**, là où l'application échouait sur ses descripteurs.

Deux conclusions :

1. **Le clavier est auto-récupérable.** Le bootloader s'atteint sans USB côté hôte : un
   firmware applicatif qui n'énumère plus n'enferme plus personne.
2. **Le matériel, le câble et le port vont bien.** Le bootloader énumère parfaitement sur
   la même chaîne. Le défaut d'énumération est donc **dans la pile USB de l'application**,
   ce qui élimine le câble, le port, et l'alimentation.

Pour ressortir du bootloader : **débrancher / rebrancher**. `0x5A` remet bien `LJMP 0x0000`
mais le périphérique ne réénumère pas sans coupure d'alimentation ; il ressort aussi seul
par temporisation d'inactivité.

### Le piège du budget de courant

Avant d'être énuméré, un périphérique USB n'a droit qu'à **100 mA**. Ce clavier allume
63 touches en RGB et ses code options autorisent 380 mA de puits sur Port6 : à pleine
luminosité dès le démarrage, il dépasse le budget et l'hôte échoue — observé, Windows
rendant successivement « échec de demande de descripteur de périphérique » puis
« ...de configuration », les deux signatures d'une alimentation qui s'effondre au milieu
d'un transfert.

`indicators.c` reste donc **au quart de la luminosité tant que `usb_is_configured()` est
faux**, avec un repli de ~6 s pour le fonctionnement sur batterie.

⚠️ **Le clavier a une batterie** : il fonctionne parfaitement sans câble, ce qui peut faire
croire à une panne USB alors qu'il n'est simplement pas relié.

### Si l'hôte n'énumère plus

> 📄 **Marche à suivre complète et autonome : [gm610-debug-linux.md](gm610-debug-linux.md)**
> — préparation, arbre de décision, et ce qu'il faut rapporter.


`utils/gm610_linux_rescue.sh`, sur une **vraie machine Linux** (une clé live suffit ;
WSL2 n'a pas d'USB natif) :

```sh
sudo ./utils/gm610_linux_rescue.sh diag     # dmesg : l'erreur exacte
sudo ./utils/gm610_linux_rescue.sh quirks   # DELAY_INIT + DELAY_CTRL_MSG, puis rebrancher
sudo ./utils/gm610_linux_rescue.sh reset    # réénumérations forcées en boucle
```

**Observé le 2026-09-13** : `error -71` (EPROTO) et `-32` (EPIPE), **jamais**
`over-current` ni `Cannot enable`. Ce n'est donc PAS un problème d'alimentation — c'est
EP0 qui répond mal ou se met en `STALL`, par intermittence : `reset` finit par obtenir
une énumération après plusieurs tentatives. Le bridage de luminosité reste une bonne
pratique, mais ce n'est pas le correctif de ce défaut-là.

### Entrer dans le bootloader depuis Linux

Le bootloader d'usine a **sa propre pile USB**, bien plus simple, et n'allume aucune LED.
S'il énumère là où l'application échoue, c'est la fenêtre de flash :

```sh
sudo python3 utils/gm610_enter_isp.py        # fait basculer, et dit chaque étape
```

Ce script ne fait **qu'une chose** : envoyer l'opcode `0x75`. Il ne lit aucun descripteur
de rapport et ne dépend d'aucune fonction d'analyse — il ne peut donc pas échouer pour une
raison sans rapport. La seule trame qui en sort est `05 75 00 00 00 00` ; les opcodes
d'écriture (`0x45`, `0x57`, `0x55`) n'y figurent que dans un commentaire.

Si la voie HID échoue — `hid` absent sous `sudo`, hidraw qui refuse, pile HID capricieuse —
la même requête part en **transfert de contrôle brut**, sans hidapi :

```sh
sudo pip install pyusb
sudo python3 utils/gm610_enter_isp_usb.py
```

C'est la requête qu'un SET_REPORT produit, à l'octet près : `bmRequestType 0x21`,
`bRequest 0x09`, `wValue 0x0305`, données `05 75 00 00 00 00` — très exactement ce que
`usb_ep0_out_irq()` teste dans `src/smk/usb.c`.

Pour lire la flash une fois en ISP :

```sh
sudo python3 utils/gm610_ispdump.py status   # n'envoie strictement rien
sudo python3 utils/gm610_ispdump.py probe    # entre en ISP, lit une page, s'arrête
```

`gm610_ispdump.py` est **en lecture seule par construction** : `send_command()` refuse
tout opcode qui écrirait en flash, effacement compris.

`dmesg` tranche : `over-current` / `Cannot enable` → c'est le courant (charger, ou un hub
alimenté) ; `error -71` sur `can't read configurations` → c'est la lenteur d'EP0.

| | |
| --- | --- |
| Matrice | ✅ validée sur l'appareil |
| Console de debug HID | ✅ validée |
| Touche `Fn` | ✅ localisée par manche de repérage, puis vérifiée |
| RGB — deux effets | ✅ validés, puits vérifiés un canal à la fois |

| Radio `bk3632` | ⚠️ **désactivée dans `meson.build`** — voir ci-dessous |

### Pourquoi la radio est désactivée

Le Bluetooth **fonctionnait** : appairage, frappe, indicateur d'état. Mais avec
`wireless: 'bk3632'`, le clavier a fini par échouer sur `GET_DESCRIPTOR(CONFIGURATION)` —
le descripteur de périphérique passait, celui de configuration non, signature d'un
transfert multi-paquets interrompu. `bb_spi.c` transfère sous `__critical`, interruptions
coupées.

La cohabitation radio / USB n'est pas traitée ; la ligne `wireless` est commentée dans
`meson.build` jusqu'à ce qu'elle le soit. Le code radio de la carte reste en place et
compile — il suffit de rétablir la ligne pour le reprendre.
