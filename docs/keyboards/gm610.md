# Newmen GM610

60 % (61 touches), RGB par touche, tri-mode (USB / Bluetooth ×3 / 2,4 GHz).

## Specs

- MCU : **SinoWealth SH68F90** — la puce se nomme elle-même, `PART = 68 f9 00 00 00`
  relu dans son bloc d'information (`FLASHCON.FAC`, cf. `src/platform/sh68f90/diag.c`)
- Rétroéclairage : RGB par touche, 5 rangées × 14 colonnes
- Sans-fil : **BK3632**, bus bit-bang — les six broches de `src/platform/bb_spi.c`
  correspondent une à une
- USB : `12C9:6001`, `SINO WEALTH` / `Newmen Bluetooth Keyboard` — **repris tels quels
  par ce portage**, au suffixe `SMK` près (voir « Identité USB »)
- Bootloader ISP d'usine conservé, `0xF000`–`0xFFFF`, jamais écrit

## Identité USB

Le clavier énumère **sous son nom d'origine**, à un suffixe près :

| | Usine | Ce portage |
| --- | --- | --- |
| VID:PID | `12C9:6001` | `12C9:6001` |
| `iManufacturer` | `SINO WEALTH` | `SINO WEALTH` |
| `iProduct` | `Newmen Bluetooth Keyboard` | **`Newmen Bluetooth Keyboard SMK`** |
| `iSerialNumber` | `0001` | `0001` |

Les trois chaînes d'usine ont été relevées dans les descripteurs `STRING` du firmware
extrait (`assets/gm610/gm610_firmware.bin`, UTF-16LE en `0x3406`, `0x343A`, `0x3452`).
Le VID:PID était déjà celui d'usine — c'est ce qui permet à l'updater OEM de reconnaître
la carte. Ne manquaient que les chaînes.

Le suffixe `SMK` sur `iProduct` est le **seul** écart volontaire : sans lui, rien ne
distinguerait ce firmware de celui d'origine dans le gestionnaire de périphériques.

### Comment une carte redéfinit ses chaînes

`src/smk/usb.c` inclut désormais `kbdef.h` et dérive ses trois chaînes de macros à
valeur par défaut :

```c
#ifndef USB_MANUFACTURER
#    define USB_MANUFACTURER "contact@carlossless.io"
#endif
#ifndef USB_PRODUCT
#    define USB_PRODUCT "SMK Keyboard"
#endif
#ifndef USB_SERIAL_NUMBER
#    define USB_SERIAL_NUMBER "0001"
#endif
```

Une carte qui ne définit rien garde donc exactement ce qu'elle avait — vérifié : la
`aula-f75` construite après ce changement contient toujours `contact@carlossless.io` /
`SMK Keyboard`, et les 256 cibles compilent. Le `kbdef.h` du GM610 définit les trois.

Coût : **+6 octets** de flash (`SINO WEALTH` est plus courte que l'adresse e-mail
qu'elle remplace, `Newmen Bluetooth Keyboard SMK` plus longue que `SMK Keyboard`).

## Code options

Identiques, **octet pour octet**, à celles de `eyooso-z11` (BYK901) et `nuphy-air60`
(BYK916) — rien à reprogrammer :

```
Code Option String: A4E063C00F000088
```

Trois conséquences qui comptent ici :

| Option | Valeur | Effet |
| --- | --- | --- |
| `OP_IOV1` | 0 | **P7.1–P7.4 en 5 V** — trois d'entre elles sont des lignes de matrice |
| `OP_SINK0` | 3 | P4.7 (horloge radio) et P7[7:5] en drain fort |
| `OP_ISP` = 1, `OP_ISPPIN` = 1 | — | **aucune entrée ISP matérielle** — voir « Récupération » |

## Brochage

Lignes et colonnes sont **identiques à la `nuphy-air60`** (même design de référence) ;
le GM610 a 14 colonnes utiles au lieu de 16, sur une grille de 21.

| | Broches |
| --- | --- |
| Lignes 0–4 | P7.1 P7.2 P7.3 P5.3 P5.4 |
| Colonnes 0–13 | P5.0 P5.1 P5.2 · P3.5→P3.0 · P2.5→P2.1 |
| Radio | CS P7.4 · SCK P4.7 · MISO P0.6 · MOSI P0.7 · MOT P0.5 · ACK P4.2 |

⚠️ **P5 porte trois choses** : colonnes 0–2 (bits 0–2), lignes 3–4 (bits 3–4, entrée),
puits bleu de la rangée 2 (bit 7). Le firmware d'usine pose la même valeur, `P5CR = 0x87`.

### RGB

Les **14 colonnes sont des sorties PWM** — les mêmes broches que les colonnes de matrice,
que le firmware rebascule en GPIO le temps du scan — et les puits sont **5 rangées ×
3 couleurs**.

| Colonne | 0 | 1 | 2 | 3–8 | 9–13 |
| --- | --- | --- | --- | --- | --- |
| Canal | `PWM40` | `PWM41` | `PWM42` | `PWM05`→`PWM00` | `PWM15`→`PWM11` |

Puits, **vérifiés sur l'appareil** (balayage à un seul canal allumé à la fois) :

| | R | V | B |
| --- | --- | --- | --- |
| L0 | P0.4 | P6.1 | P0.3 |
| L1 | P6.7 | P6.2 | P6.6 |
| L2 | P0.2 | P6.3 | P5.7 |
| L3 | P4.5 | P6.4 | P4.6 |
| L4 | P4.4 | P6.5 | P4.3 |

## Raccourcis

Aux positions **et temporisations** du firmware d'usine.

| | |
| --- | --- |
| `Fn` | rangée basse, colonne 13 |
| `Fn + \` | effet suivant |
| `Fn + [` / `]` | vitesse − / + |
| `Fn + ;` / `'` | luminosité − / + |
| **`AltGr`** *(sans Fn)* | **←** — `Fn + AltGr` rend l'AltGr |
| **`Menu`** *(sans Fn)* | **↓** — `Fn + Menu` donne **↑** |
| **`Ctrl droit`** *(sans Fn)* | **→** — `Fn + Ctrl droit` rend le Ctrl |
| `Fn + J` / `Fn + M` | **Origine** / **Fin** |
| `Fn + Maj` (gauche **ou** droit) `+ ↑` / `↓` | **PgPréc / PgSuiv** |
| `Fn + Échap` | **`` ` `` et `~`** |
| `Fn + U` | Impr. écran |
| **`Fn + Ctrl gauche`** | **bascule la compensation AZERTY** |
| `Fn + D` | balayage de diagnostic des puits RGB |
| **`Fn + B`, ~3 s** | **retour dans le bootloader** — tout rouge ~0,5 s, puis noir |
| `Fn + Tab`, ~3 s | bascule USB ↔ sans-fil *(radio désactivée, voir plus bas)* |
| `Fn + Q` / `W` / `E` | canaux Bluetooth 1 / 2 / 3 |
| `Fn + G`, ~3 s | liaison 2,4 GHz |

⛔ **Un maintien se compte en battements de l'ISR systick, jamais en tours de boucle
principale.** 100 battements de 30 ms = 3 s, la temporisation d'usine.

La première version comptait 6 000 tours de boucle, calibrés à ~2 kHz en USB au repos. Mais
**la boucle principale n'a pas de cadence** : en Bluetooth non connecté elle s'effondre — la
radio retente sa liaison, et le témoin faisait repeindre les 70 cases à chaque trame. Le
maintien devenait alors interminable, c'est-à-dire que **`Fn + Tab` et `Fn + B` étaient
muets dans l'état même où ils servent**. Mesuré sur l'appareil.

La cadence matérielle, elle, est connue et stable : sous-trame LED de 400 µs et scan matrice
de 100 µs alternés (`src/platform/sh68f90/systick.c`) → 2 000 sous-trames/s, et une trame =
15 sous-trames → **133 trames/s**. `indicators_ticks` les divise par 4 : un battement toutes
les 30 ms, qui tient dans un octet — donc atomique à lire sur 8051.

### La compensation AZERTY — **active par défaut**

Les capuchons portent la disposition **US International**. Quand l'hôte est réglé en
**AZERTY français**, les deux se contredisent : la touche marquée `A` écrit `q`, la touche
`1` écrit `&`. Ce mode fait porter la traduction par le **clavier** — on frappe ce qui est
écrit sur les capuchons, et le bon caractère sort, **sans rien changer côté PC**.

`src/keyboards/gm610/gm610_layout.c` est porté depuis la carte `aula-f75`, où la table a
été établie et vérifiée. Elle est indépendante du clavier : c'est de la traduction de
keycodes, pas du brochage.

| | |
| --- | --- |
| Bascule | **`Fn + Ctrl gauche`** |
| Défaut | **active** |
| Persistance | `user_settings.ul_speed` — libre ici, cette carte n'a pas d'underglow |

⚠️ **`ul_effect` est déjà pris** sur cette carte : `kb.c` y persiste le mode de liaison.
Ne pas confondre les deux champs.

⚠️ **La restauration se fait dans `indicators_validate_settings()`, pas dans `kb_init()`** —
`main.c` appelle `kb_init()` **avant** `restore_settings()`, il n'y aurait rien à lire. Le
même piège a déjà coûté un aller-retour sur le mode de liaison.

**Le découpage tick / task est obligatoire.** `gm610_layout_tick()` fait courir les
minuteurs depuis la sous-trame LED (ISR, ~400 µs) ; `gm610_layout_task()` vide la file
d'émission depuis la boucle principale. `send_keyboard_report()` traverse la pile de
rapports et reste injoignable depuis une ISR sans collision de recouvrement SDCC — ce que
`utils/check_interrupts.py` casse le build pour empêcher.

#### L'annonce visuelle

Le clavier dit dans quel mode il est, en éclairant **deux touches clignotantes** :

| | |
| --- | --- |
| **F** et **R**, en **bleu** | compensation AZERTY active |
| **U** et **S**, en **blanc** | disposition US brute |

~5 s au démarrage, ~1,5 s à chaque bascule. Les lettres portent le sens ; la couleur ne fait
que le rendre lisible d'un coup d'œil.

⚠️ Les positions se comptent sur la **couche de base**, et la rangée est
`Tab Q W E R T Y U I O P [ ] \` : **`U` est en colonne 7**, la 6 étant `Y`. Première version
allumait `Y` — relevé sur l'appareil. Le même décalage avait mis `Impr. écran` sur `Y` au
lieu de `U`.

### ⛔ Pas de touches média — choix du propriétaire

La collection consommateur (`page=0x000C`) est **énumérée et libre**, et `report.h` expose
déjà les usages (`AUDIO_VOL_UP`, `TRANSPORT_PLAY_PAUSE`…). Les ajouter ne coûterait rien.

**Elles ne sont volontairement pas câblées** : le propriétaire n'en a pas l'usage avec son
installation. Décision prise le 2026-09-13, à ne pas reproposer.

### Le pavé fléché, et deux manques du 60 %

Ce clavier n'a **aucune flèche**, et la table d'usine n'en contient **nulle part** — vérifié
sur ses 126 enregistrements. Il n'a pas non plus de touche **accent grave** : sa rangée du
haut va d'`Échap` à `Retour arrière` sans elle.

```
   AltGr    Menu    Ctrl droit          Fn + J   Origine
     ←        ↓         →               Fn + M   Fin
              ↑ avec Fn
```

**Les trois touches de droite sont inversées** : flèche sans `Fn`, fonction d'origine avec.
Un vrai pavé fléché sous la main droite, sans modificateur à tenir. Le `↑` est le seul qui
demande `Fn` — il n'y a plus de quatrième touche pour l'accueillir.

⚠️ **AltGr et Ctrl droit ne sont plus directs.** `Ctrl` reste disponible à gauche ; quant à
AltGr, la compensation AZERTY l'injecte elle-même pour `@ # [ ] { }` etc., donc on ne le
tape presque jamais à la main.

⚠️ La touche **Menu perd sa fonction d'origine** — il n'y a plus de `KC_APP`.

⚠️ La flèche bas étant sur la couche de BASE, **`Maj + Menu` seul suffit pour PgSuiv**, sans
`Fn` — asymétrie assumée, conséquence directe de l'inversion.

Les **deux** `Maj` conviennent, vérifié sur l'appareil. Le droit est juste au-dessus de `Fn`
et des flèches, donc c'est l'accord d'une seule main.

Une version antérieure ne testait que le `Maj` gauche, et sur l'appareil **seul le droit
répondait** — alors que les deux bits sont distincts (`KC_LSFT` → bit 1, `KC_RSFT` → bit 5).
Aucune explication n'a été trouvée à distance ; accepter les deux et ne masquer que le `Maj`
réellement tenu a réglé les deux cas d'un coup. C'est un contournement, pas un diagnostic —
si le sujet revient, une trace console sur `get_mods()` à l'appui de la flèche dirait en une
seconde quel bit est réellement posé.

⚠️ **`Fn + Maj + ↑/↓` retire le `Maj` du rapport** — et seulement celui qui est réellement
tenu. Sans ça l'hôte lit
`Maj + PgPréc`, c'est-à-dire « sélectionner une page » et non « tourner une page » — le
contraire de ce qu'on demande. `set_mods_mask()` masque le bit dans le rapport sortant sans
toucher à l'état réel du modificateur, donc le relâchement du `Maj` reste correctement vu.

Le code substitué est mémorisé **par flèche** : la touche doit se relâcher sur le même code
qu'à l'appui, même si le `Maj` a été lâché entre-temps — sinon l'hôte garderait un `PgPréc`
enfoncé indéfiniment.

`Fn + Échap` donne `` ` `` et `~`. Le firmware d'usine y remettait `Échap`, ce qui ne
servait à rien puisque la touche le donne déjà sans `Fn`.

## Effets

Deux, volontairement :

- **battement** — deux systoles rapprochées puis une longue diastole, la teinte dérivant.
  C'est un battement de cœur, pas une respiration. Diviseur de vitesse propre, quatre fois
  plus court : au pas commun un cycle durerait dix secondes.
- **goutte d'eau sur le lac** *(défaut)* — chaque frappe jette une goutte, une couronne
  s'en éloigne d'un cran par trame, sa teinte glissant avec la distance. Distance en
  approximation octogonale (`max + min/2`) et non en losange : sur un clavier une rangée
  et une colonne font le même pas physique, les couronnes doivent être rondes.

  Le **lac au repos est un violet qui respire**, fondu complet en **3 s** : un triangle
  entre un indigo et un magenta, vert maintenu à zéro — c'est ce qui garde la couleur
  violette à tout point du fondu. Calculé **une fois par trame**, pas par case, sinon les
  70 cases de l'image reliraient la même chose soixante-dix fois.

  La teinte des couronnes monte de **15 par cran d'âge** : sur les 17 crans d'une onde,
  cela fait 255, soit le **tour complet** du cercle chromatique. La première version
  montait de 6 — 40 % du cercle — et les couronnes paraissaient monochromes à l'œil.

  ⚠️ Les deux cadences sont calées sur le **battement de 30 ms**, pas sur la trame de
  7,5 ms ni sur la vitesse de l'effet : « trois secondes » doit valoir trois secondes quel
  que soit le réglage de vitesse.

La position d'une frappe ne passe pas par `kb_process_record()`, qui ne reçoit qu'un code
de touche : `user_matrix.c` tient un instantané par colonne (`user_matrix_pressed()`) que
le moteur d'éclairage interroge, une colonne par sous-trame.

## ⛔ Récupération — à lire avant de flasher

**Cette carte n'a aucune entrée ISP matérielle.** `OP_ISP = 1`, et les 4 096 octets du
bootloader d'usine ne lisent pas un seul GPIO. Il n'existe donc **aucun sauvetage par
combinaison de pads**.

D'où la règle, apprise à la dure le 2026-09-13 : **le firmware doit offrir au moins une
porte vers le bootloader qui ne dépende pas de l'USB.** C'est `Fn + B` maintenu ~3 s, qui
éteint le RGB puis appelle `isp_jump()`.

### ✅ Vérifié le 2026-09-13 : `Fn + B` fonctionne, et le bootloader énumère

Maintenu ~3 s, `Fn + B` fait apparaître `0603:1020` avec ses trois collections — clavier,
canal commande (report 5), canal transfert (report 6) — et **Windows le donne pour
`Status : OK`**, là où l'application échouait sur ses descripteurs.

Deux conclusions :

1. **Le clavier est auto-récupérable.** Le bootloader s'atteint sans USB côté hôte : un
   firmware applicatif qui n'énumère plus n'enferme plus personne.
2. **Le matériel, le câble et le port vont bien.** Le bootloader énumère parfaitement sur
   la même chaîne. Le défaut d'énumération est donc **dans la pile USB de l'application**,
   ce qui élimine le câble, le port, et l'alimentation.

Pour ressortir du bootloader : **débrancher / rebrancher**. `0x5A` remet bien `LJMP 0x0000`
mais le périphérique ne réénumère pas sans coupure d'alimentation ; il ressort aussi seul
par temporisation d'inactivité.

### ✅ La porte de secours, prouvée là où elle sert

Vérifié le 2026-09-13, **en Bluetooth non appairé** — l'état où la boucle principale est
affamée et où la première version restait muette : `Fn + B` maintenu ~3 s fait passer le
clavier au rouge, puis au noir, puis `0603:1020` apparaît avec ses trois collections, zéro
périphérique en erreur côté hôte.

C'est la garantie qui manquait au premier flash : **un firmware applicatif qui n'énumère
plus n'enferme plus personne.**

### La porte de secours doit vivre dans l'ISR

`Fn + B` **annonce son départ** : tout le clavier passe au rouge une demi-seconde, puis
s'éteint, puis le bootloader démarre. Le décompte et le saut se font dans `fx_tick()`,
c'est-à-dire dans l'**ISR systick**, pas dans `kb_update()`.

Deux raisons, les deux vécues :

1. **La boucle principale peut être affamée.** En Bluetooth non connecté, la radio retente
   sa liaison et le témoin d'état fait repeindre l'image : `kb_update()` s'espace. Or c'est
   exactement l'état où cette porte doit servir. L'ISR, elle, a une cadence matérielle.
2. **Sans annonce, un saut réussi est indiscernable d'un raccourci muet.** Sur batterie,
   sans câble, `indicators_all_off()` puis le bootloader, ça ressemble à un clavier qui
   s'éteint sans raison — c'est ce qui a fait croire que `Fn + B` ne répondait pas.

### Le piège du budget de courant

Avant d'être énuméré, un périphérique USB n'a droit qu'à **100 mA**. Ce clavier allume
63 touches en RGB et ses code options autorisent 380 mA de puits sur Port6 : à pleine
luminosité dès le démarrage, il dépasse le budget et l'hôte échoue — observé, Windows
rendant successivement « échec de demande de descripteur de périphérique » puis
« ...de configuration », les deux signatures d'une alimentation qui s'effondre au milieu
d'un transfert.

`indicators.c` reste donc **au quart de la luminosité tant que `usb_is_configured()` est
faux**, avec un repli de ~6 s pour le fonctionnement sur batterie.

⚠️ **Le clavier a une batterie** : il fonctionne parfaitement sans câble, ce qui peut faire
croire à une panne USB alors qu'il n'est simplement pas relié.

### Si l'hôte n'énumère plus

> 📄 **Marche à suivre complète et autonome : [gm610-debug-linux.md](gm610-debug-linux.md)**
> — préparation, arbre de décision, et ce qu'il faut rapporter.


`utils/gm610_linux_rescue.sh`, sur une **vraie machine Linux** (une clé live suffit ;
WSL2 n'a pas d'USB natif) :

```sh
sudo ./utils/gm610_linux_rescue.sh diag     # dmesg : l'erreur exacte
sudo ./utils/gm610_linux_rescue.sh quirks   # DELAY_INIT + DELAY_CTRL_MSG, puis rebrancher
sudo ./utils/gm610_linux_rescue.sh reset    # réénumérations forcées en boucle
```

**Observé le 2026-09-13** : `error -71` (EPROTO) et `-32` (EPIPE), **jamais**
`over-current` ni `Cannot enable`. Ce n'est donc PAS un problème d'alimentation — c'est
EP0 qui répond mal ou se met en `STALL`, par intermittence : `reset` finit par obtenir
une énumération après plusieurs tentatives. Le bridage de luminosité reste une bonne
pratique, mais ce n'est pas le correctif de ce défaut-là.

### Entrer dans le bootloader depuis Linux

Le bootloader d'usine a **sa propre pile USB**, bien plus simple, et n'allume aucune LED.
S'il énumère là où l'application échoue, c'est la fenêtre de flash :

```sh
sudo python3 utils/gm610_enter_isp.py        # fait basculer, et dit chaque étape
```

Ce script ne fait **qu'une chose** : envoyer l'opcode `0x75`. Il ne lit aucun descripteur
de rapport et ne dépend d'aucune fonction d'analyse — il ne peut donc pas échouer pour une
raison sans rapport. La seule trame qui en sort est `05 75 00 00 00 00` ; les opcodes
d'écriture (`0x45`, `0x57`, `0x55`) n'y figurent que dans un commentaire.

Si la voie HID échoue — `hid` absent sous `sudo`, hidraw qui refuse, pile HID capricieuse —
la même requête part en **transfert de contrôle brut**, sans hidapi :

```sh
sudo pip install pyusb
sudo python3 utils/gm610_enter_isp_usb.py
```

C'est la requête qu'un SET_REPORT produit, à l'octet près : `bmRequestType 0x21`,
`bRequest 0x09`, `wValue 0x0305`, données `05 75 00 00 00 00` — très exactement ce que
`usb_ep0_out_irq()` teste dans `src/smk/usb.c`.

Pour lire la flash une fois en ISP :

```sh
sudo python3 utils/gm610_ispdump.py status   # n'envoie strictement rien
sudo python3 utils/gm610_ispdump.py probe    # entre en ISP, lit une page, s'arrête
```

`gm610_ispdump.py` est **en lecture seule par construction** : `send_command()` refuse
tout opcode qui écrirait en flash, effacement compris.

`dmesg` tranche : `over-current` / `Cannot enable` → c'est le courant (charger, ou un hub
alimenté) ; `error -71` sur `can't read configurations` → c'est la lenteur d'EP0.

## Flasher — `sinowisp`, sous Linux

✅ **Vérifié sur l'appareil le 2026-09-13.** C'est la voie de flash qui ne dépend ni de
Windows ni de l'updater OEM :

```sh
sinowisp write -p sh68f90 build/gm610_default_smk.hex
```

L'entrée est le `.hex` de SMK **tel quel**. ⛔ Ne jamais lui donner une image déjà convertie
en disposition JTAG : le bootloader permute les cinq octets lui-même, une seconde
permutation ferait boucler le clavier dans son propre bootloader.

⛔ **Une version de cette documentation interdisait `sinowisp write` sur cette carte, en
« règle dure », et c'était faux.** L'argument : son armement, « le tremplin en
`firmware_size-5` », différerait de celui du GM610, « l'octet `0xEFFB` ». Or
`61440 − 5 = 0xEFFB` — **c'est le même octet, décrit deux fois**. Le tour de l'octet 0 de
l'updater OEM (`0x00` à l'offset 0 pendant le flash, page 0 réécrite en dernier) est une
protection supplémentaire contre un flash interrompu, pas le mécanisme d'armement du
bootloader.

carte **sans radio**, qui énumère irréprochablement.

Le Bluetooth fonctionne — appairage, frappe, témoins d'état. Mais l'hôte finit par échouer
sur `GET_DESCRIPTOR`, et **deux gardes successives n'ont pas suffi** :

| | |
| --- | --- |
| **v1** — silence pendant l'énumération, rationnement hors configuration | ❌ insuffisante sur l'appareil |
| **v2** — rationnement dès que la liaison n'est pas connectée | ⚠️ écrite, **non vérifiée** |

Ce que la v1 a appris, au prix d'un aller-retour : un **reflash fait perdre l'appairage**, le
clavier redémarre en sans-fil puisque le mode est persisté, et la liaison **cherche** — l'état
où le superviseur travaille le plus. Or la v1 laissait la radio à plein régime dès que l'USB
était configuré : elle ne protégeait justement pas cet état.

La v2 comble ce trou. Elle reste à éprouver.

**Piste suivante si la v2 ne suffit pas** : ne pas réduire le *nombre* de fenêtres
`__critical` mais leur *durée* — découper les transferts de `bb_spi.c` pour rendre la main
entre les octets. C'est le vrai correctif ; le rationnement n'est qu'un contournement.

### La garde radio, dans le détail

La radio ne parle à plein régime que si l'USB est configuré **et** la liaison connectée :

| État | La radio |
| --- | --- |
| USB configuré **et** liaison connectée | plein régime |
| USB configuré, liaison **non connectée** | **une itération sur huit** |
| USB non configuré, dans les 3 s après le démarrage ou une perte de configuration | **silence total** |
| USB non configuré, au-delà | une itération sur huit |

La deuxième ligne a coûté un aller-retour. La première version rendait `true` dès que l'USB
était configuré — c'était un trou, pour deux raisons :

1. **La radio travaille le plus quand la liaison n'est PAS établie.** Le superviseur retente
   en boucle et `bb_spi` enchaîne les transferts sous `__critical`. C'est exactement l'état
   où un reflash laisse le clavier, appairage perdu — donc l'état le plus exposé.
2. **« Énumération finie » ne veut pas dire « plein régime autorisé ».** L'hôte continue
   d'émettre des transferts de contrôle bien après, et une fenêtre `__critical` trop longue
   les casse tout autant : il réinitialise alors le périphérique, et le cycle recommence.

On ne peut pas non plus distinguer de façon fiable « sur batterie » de « le câble vient
d'être branché ». Faute de savoir, on rationne plutôt que de choisir.

### La cohabitation radio / USB, mesurée

Avant la garde, en mode sans-fil, une veille du bus relevait **six apparitions et six
disparitions en 190 s**, la première coupure dès la 36ᵉ seconde.

Avec `rf_service_allowed()`, sur une veille de **390 s** : une seule disparition, à la
3ᵉ seconde — le rebranchement volontaire — puis **382 secondes sans un seul décrochage**. Et
la frappe Bluetooth reste sans latence perceptible, ce qui était le risque du rationnement à
une itération sur huit.
